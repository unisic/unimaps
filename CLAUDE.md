# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

**Unimaps** (repo `unisic/unimaps`, GPL-3.0-or-later), a live transit map for Bielsko-Biała (Komunikacja Beskidzka + MZK) and Metropolia GZM: a Next.js 16 (App Router, TypeScript strict) app where **one Node process** serves the Leaflet map UI, a JSON API, a GTFS-RT VehiclePositions protobuf feed, and runs the live scraper poller in-process. The KB upstream is `https://komunikacjabeskidzka.kiedyprzyjedzie.pl` (KiedyPrzyjedzie). App identity is Unimaps, but the `KB_*` env vars, `kb:*` storage keys, `kb-output` volume and `Symbol.for("kb-gtfs.*")` keep their names on purpose (renaming breaks deployments and user state). The `lib/` layer is a deliberate behavioral-parity TypeScript port of a former Python codebase — see Gotchas. README.md (English) documents endpoints and key env vars; `.env.example` lists all of them.

## Commands

```bash
npm run dev          # next dev on port 8080 (poller starts too — dev mode scrapes upstream)
                     #   PORT=8081 npm run dev when 8080 is taken (Steam's steamwebhelper listens on 127.0.0.1:8080)
npm run build        # next build (output: "standalone")
npm start            # node scripts/start-server.mjs — syncs .next/static + public into
                     #   .next/standalone, then runs node .next/standalone/server.js
                     #   (falls back to `next start` if no standalone build exists)
npm run lint         # eslint .
npm run typecheck    # tsc --noEmit
npm test             # node --import tsx --test "test/**/*.test.ts" — pure-function tests
npm run build:gtfs -- --date 2026-07-05   # static GTFS builder CLI (logic lives in lib/gtfs-builder.ts)
                     #   flags: --date YYYY-MM-DD, --out DIR, --concurrency N, --no-zip
```

Verification is `npm run typecheck` + `npm run lint` + `npm test` + exercising the running app (`/api/health` shows status/scan counters). CI (`.github/workflows/ci.yml`) runs all four plus `next build` and `npm audit --audit-level=high`; it must never run `build:gtfs` (hits the live upstream). Tests in `test/` **pin Python-parity semantics** — a failing parity test means a regression in lib code, never "fix" the expectation.

Default port is **8080** everywhere (dev, start script, Dockerfile, compose), not 3000. Docker: `docker compose up -d --build`; healthchecks hit `/api/health`.

Config is via `KB_*` env vars (see `.env.example`), all optional. `lib/config.ts` reads them **at module load** — changing one requires a process restart.

## Architecture

### Backend data flow

```
instrumentation.ts register()            (Next instrumentation hook, nodejs runtime only)
  └─> lib/poller-singleton.ts startPoller()   (idempotent; singleton on globalThis)
        └─> lib/poller.ts LivePoller          (background loop, in-memory positions Map)
              └─> lib/kb-api.ts KbApi         (fetch + p-limit concurrency 40, retries)
                    └─> upstream API
```

- Routes under `app/api/` read poller snapshots: `/api/vehicles` (`toJson()`), `/api/gtfs-rt.pb` (`toProtobuf()`, gtfs-realtime-bindings), `/api/stops`, `/api/health`. Every route **also** `await startPoller()` as a lazy fallback, so the poller starts even if instrumentation didn't fire.
- `/api/geocode?q=` (address search for a connection from or to a point, `from=`/`to=geo:LAT,LON` = every pole within `walk` m, 200-1500, default 800, as access / egress walk; the client keeps the choice in `kb:walkMax`) proxies Photon (`KB_GEOCODER_URL`, `off` = 404) inside a per-city bbox: memo 1000 queries / 24 h, at most 4 requests in flight (more = 429), one client request per typing pause.
- `/api/connections` takes `arriveBy=true` (needs `time`, else 400): `time` becomes the latest arrival and the answer is the `limit` latest-departing connections that make it, same day only (no next-day fallback).
- `/api/line?name=[&op=KB|MZK][&date=]` (`?city=gzm` = GZM) feeds the line view: `lineTimetable()` (`lib/router.ts`) over the BB router index or the GZM feed's, the 12 busiest stop patterns active on the date with each trip's departure per stop in minutes from that midnight. O(trips) scan per request, `public, max-age=3600`, rate-limited; no index yet = `warming()`.
- `/api/push` (`lib/push-alerts.ts` + `lib/web-push.ts`, node:crypto only: VAPID ES256 + RFC 8291 aes128gcm, pinned by the RFC test vector) fires a "Powiadom mnie" alert as a web push with the app closed: a browser POSTs `{subscription, alert}` (endpoint allowlisted to the push services, it is an outbound POST target), a 30 s tick armed only while alerts are pending reads each alerted stop's board (`lib/stop-board.ts` `stopBoard()`, the departures route's own micro-cached board; GZM from the local feed) and pushes what the shared `alertAction` (`lib/shared/alerts.ts`) decides. At most 300 alerts, 6 per subscription, each dropped at `until`; 404/410 from the push service drops the subscription. VAPID pair + alerts in `KB_PUSH_DIR` (`output/push`, 0600); a lost `vapid.json` orphans every subscription. The page watcher still fires too (same tag, one notification).
- Passthrough routes (`/api/trip/[tripId]`, `/api/trip_execution`, `/api/stop/[designator]/departures|timetable`) proxy the upstream directly, gated by `lib/rate-limit.ts` (in-memory per-IP token bucket) and `lib/api-helpers.ts` validation.
- Poller rhythm (defaults, `lib/config.ts`): full scan of all ~956 stops every 90 s, smart incremental scan every 30 s, position refresh of active vehicles every 10 s (+ work time; upstream itself only moves a KB position every ~6–18 s). MZK (`lib/mzk-poller.ts`) polls its whole fleet every 5 s. It discovers `trip_execution_id`s from departures (the only way to get positions — they live in a different ID space than static `trip_id`). The loop runs under `supervise()` — a crash restarts it with capped backoff (`loopRestarts` in health). The stop list reloads daily (`KB_STOPS_RELOAD_SEC`) with an atomic map swap; a failed (or empty) reload keeps the old list. The MZK stop list follows the same rule (`MzkPoller.loadStops`) and is additionally reloaded, at most every 10 min, when a running course references an unknown stop symbol — upstream re-versions its stop data (2026-09-30), so a list loaded once at boot goes stale.
- `/api/health` returns `"degraded"` + HTTP 503 (flips Docker healthchecks) when the scan loop stalls or upstream contact exceeds `KB_HEALTH_STALE_SEC` (1200 s > the 600 s overnight all-cached window). Deliberately no vehicle-count condition — 0 at night is normal.
- `lib/gtfs-refresh.ts` (armed from `startPoller()`, HMR-safe singleton) rebuilds the GTFS feed in-process: immediately when `output/gtfs` is missing (fresh Docker volume), else daily after `KB_GTFS_BUILD_HOUR` Warsaw time, then invalidates the stop-directions/lines caches. It exists because the standalone image ships no tsx/scripts — builder logic lives in `lib/gtfs-builder.ts`, `scripts/build-gtfs.ts` is just the CLI. Compose mounts the named volume `kb-output:/app/output`.
- `lib/shape-store.ts` is the **road-shape store**: road-following geometry for KB stop patterns (`lib/shape-patterns.ts` — keyed by stop ids + applied detour, routed server-side through OSRM by `lib/osrm.ts`, one throttled worker, ≥1 s between requests on the public demo host) and MZK variants (operator API, `lib/mzk-shape.ts`). Persisted to `output/shapes/route-shapes.v1.json` (atomic sync writes + `.bak`, lock file = single writer; a non-owner is read-only), refreshed gradually (one entry per 2 min, road shapes after `KB_SHAPES_MAX_AGE_DAYS`), seeded from the GTFS patterns after start and every nightly build. A new pattern gets a straight entry at once; a road entry is never downgraded; OSRM failures pause the worker (circuit breaker) and never touch `/api/health` status. `/api/shapes?ids=` only reads the store (never routes/fetches), ids are `<key>.<rev6>` so exact hits are `immutable`.
- **Stop merging (KB + MZK).** `lib/stop-merge.ts` `mergeStops(kb, mzk, { mzkDirs })` is a pure, order-independent global assignment (Hungarian per connected component, max cardinality first): eligible = ≤ 35 m, or ≤ 120 m with matching cleaned names; a pair whose travel directions are opposite (KB `dirs` from GTFS vs MZK bearings learned by `lib/mzk-stop-dirs.ts` from the stop ORDER of running courses, persisted to `output/mzk-stop-dirs.v1.json`, dropped when a stop moves/vanishes) is eligible only ≤ 12 m. The learned MZK bearings steer the pairing ONLY — they never reach the wire (arrows stay a KB/GTFS feature). A bus station (`isStation`) pairs only ≤ `MERGE_HUB_M` = 35 m and fans its departures/timetable out to the other same-name MZK stops in that radius (`mzkSymbols`, primary first; Czechowice-Dz. D.A. = 2366 + 2367). Those extras are folded into the hub: no entry of their own (one marker per station), their symbols alias to it in both lookups (server `indexMergedStops`, client `byDesig`). Its cleaned name is the bare `DWORZEC`, which matches every MZK `<street> Dworzec`, so a wider radius pulls street stops in: Bielsko-Biała D.A. is KB-only (MZK 343/341/342/264/469 at 89-183 m are stops of their own); those stops stay MZK-only entries with their own position (MZK trip timelines are drawn at the resolved stop's coordinates). `lib/merged-stops.ts` is the ONE memoized source (`getMergedStopsView()` in poller-singleton, keyed on input identity) for `/api/stops` (ETag/304; `no-cache` + `partial: true` while one operator's list is missing), the departures/timetable routes and `/api/health` — never re-merge ad hoc, never use the `getMergedStop()` global registry in routes, never `import()` a stateful module dynamically in a route (tsx loads a second copy). The departures/timetable routes answer `warnings: ["kb"|"mzk"]` (and the timetable `no-store`) when an upstream fetch failed — a failed fetch is not "no departures". `MzkApi` caches getRealtime 5 s / getAtomicSchedule 15 min (in-flight deduped, failures never cached). Tests pin real captured data (`test/fixtures/stop-merge-live.json`).
- The pollers attach route info per vehicle (`lib/route-info.ts`, isolated in try/catch so it can never abort a refresh): shape key, `fixAt` (KB has no upstream fix time — midpoint of the poll window that saw the change; MZK `lastPingDate`), along-route `distM`, and a cruise `speed` taken only from consecutive moving fixes outside stop zones. `vehicleExtras()` puts them on the wire (`shape`, `dist_m`, `fix_at`, `next_stop_seq`, `speed`) — `vehicleToJson` (the Python port) stays untouched. `/api/vehicles` also sends `X-Server-Time` (a header, so unchanged payloads still dedupe in SWR). Trip responses carry `shape_id` + `shape_status` (`road|pending|none`); `/api/connections` legs carry `shape_id`.
- **KB delay = upstream's value only while its stop index is trustworthy.** Upstream registers a stop only when one of its 6–18 s GPS samples lands in the stop zone; a bus that passes stops without slowing is never registered, `vehicle_trip_index`/`next_departure_index` stall and `estimates[0]` is clamped to "now" for the stale stop, so `parsePosition`'s delay (`estimates[0] − plan(next stop)`, still the untouched Python-parity formula) grows +1 min/min (+5 → +11 on a bus that is on time). `lib/kb-progress.ts` (pure, straight stop-to-stop geometry, called from `LivePoller.attachProgress` on EVERY poll before `attachRouteInfo`) places the bus monotonically (upstream's last registered stop = hard lower bound, so the outbound leg of a loop can't steal a return-leg fix) and, only when the bus is > 120 m beyond the stop upstream calls next, overwrites `pos.delay` with the schedule deviation at the real position. `pos.delayUp` keeps the raw value — `isFeedStale()` MUST test it (a GPS delay must not hide a frozen feed). While stale, `/api/vehicles` also carries `delay_src` (`gps`|`gps-held`|`unknown` = delay withheld/null) and `geo_seq` (GPS index of the last passed stop); the client prefers `geo_seq` over `current_stop_sequence` as the `findActiveStop` hint (a stale hint puts a bus on the OUTBOUND leg of a loop) and `attachRouteInfo` feeds the GPS indices to `kbDistAlong`. In sync nothing changes. `KB_GPS_DELAY=0` disables it; `/api/health` → `stale_index` counts affected vehicles. Cold start (restart) mid-loop with a stale index is ambiguous and falls back to upstream's value.
- **Loop / twin-stop trips.** Out-and-back patterns (line 120 Szczyrk Biła, 37 % of KB trips) use *twin* stops (opposite sides of one road, 14–50 m apart, km apart along the route) and upstream's stop index can freeze for minutes. `kbDistAlong` is continuity-first (previous `dist_m` as hint, window widened by the poll gap via `kbAheadM`, then the vti window fed with the GPS indices, then a strict search); `findActiveStop` honours `at_stop` + the hint within 90 m and prefers, among near poles, the one closest to the hint index; TripView reads `dist_m` against the shape chainage (`lib/shared/trip-progress.ts`, pure — `react-hooks/refs` is a lint ERROR, so never keep progress state in a ref during render).
- **MZK "course not begun".** For a course that has not started OnTime sends a placeholder: `delaySec = max(-60, now − first scheduled departure)` and every `plannedDeparture = scheduled + that`. `lib/mzk-state.ts isMzkNotStarted()` classifies it once (orderInCourse 0 and lastStopOrderNo null, or 0 with reachedMeters < 30; bus > 400 m from the first stop = started); the poller publishes `delay: null` + `not_started` (via `vehicleExtras`), live trips carry no per-stop estimates (none at all in publicly cached static trips), departure rows get the earliest possible time + `not_started`, fleet-tracker neither counts nor archives such courses. A `not_started` row/vehicle must never yield a delay from ANY source (`resolveTiming` enforces it).
- **Stop merging (KB ↔ MZK).** `lib/stop-merge.ts` is an order-independent global assignment (direction-aware; MZK stop bearings are learned from running vehicles' stop order, `lib/mzk-stop-dirs.ts`, persisted to `output/mzk-stop-dirs.v1.json`); one memoized view (`getMergedStopsView()`, `lib/merged-stops.ts`) feeds `/api/stops` (ETag/304), departures and timetable — never an ad hoc re-merge. The MZK stop list reloads daily and when a running course references an unknown symbol (OnTime re-versioned all stops on 2026-09-30); a failed/empty reload keeps the old list. Station hubs (D.A.) also list the same-name MZK stops within 35 m (`mzkSymbols`). A failed upstream leg is reported as `warnings` instead of looking like "no departures".
- **Departures board.** Two time dialects (KB relative "N min" strings floored, `time: null` + `at_stop`, far-off rows as "HH:MM", `time_diff` in MINUTES; MZK absolute instants + vehicle delay in SECONDS). The server normalises rows to epoch seconds (`lib/shared/departures.ts`: `plan_ts`, `eta_ts`, `delay_sec`, `row_key`, `server_ts`), the client resolves ONE canonical ETA per row (`resolveTiming`) and uses it for both the label and the order (printed minute → line → plan → key; rows > 60 s past due are hidden). StopView polls via `lib/client/live-poll.ts` (10 s ±15 %, 12 s per-request timeout, backoff, catch-up on visibility/pageshow/focus/online, watchdog, never two requests in flight; a failing refresh never wipes the list, a stale stamp appears after 45 s). The route builds each board behind a 4 s micro-cache (`lib/departures-board-cache.ts`, keyed by merged-stop identity) and answers 502 when every upstream leg failed.
- `lib/stop-directions.ts` derives stop direction arrows from pre-built GTFS files in `output/gtfs/`; missing files silently yield no arrows. Cached per process until `invalidateStopDirections()`/`invalidateLines()` (called after a rebuild); `/api/stops` re-serializes when either the stop-list or the directions-map identity changes.
- `lib/stop-directions.ts` derives stop direction arrows from pre-built GTFS files in `output/gtfs/`; missing files silently yield no arrows. Cached per process until `invalidateStopDirections()`/`invalidateLines()` (called after a rebuild); `/api/stops` re-serializes when either the stop-list or the directions-map identity changes (see "Stop merging").

- **Metropolia GZM (second city).** `lib/gzm-feed.ts` (zbiorkom GZM GTFS zip in `output/gzm/gtfs.zip`, streamed parse into one immutable `GzmFeed`: stops body + ETag, lines, trips with dates, shapes, a `RouterIndex` from `buildRouterIndex`) and `lib/gzm.ts` (`GzmLive`, singleton `Symbol.for("kb-gtfs.gzm")`, started from `instrumentation.ts` and lazily by every GZM route branch via `startGzm()`). It is isolated from `startPoller()`: a GZM failure never touches BB data, and the `/api/health` → `gzm` block never flips `status`. zbiorkom positions are polled every 20 s phased 3 s after zbiorkom's own 20 s grid; SDIP (`planner/v`, JSESSIONID cookie) overlays positions every 5 s only while a GZM request came in within 120 s, with a 5 min pause after 3 failures; its dated fix wins for as long as SDIP reports the vehicle (zbiorkom serves the same positions 5-60 s later, so a time comparison hands a standing bus back to an older spot), a vehicle missing from one SDIP list keeps its sample. A record joins a trip ONLY when every upcoming (seq, scheduled departure) pair matches a trip of its line active today or yesterday (exact first, then within `MATCH_SLACK_SEC` = 30 s: Tczew's live calls run 5 s off zbiorkom's own GTFS), brigade breaks ties; a bus whose next call is the first stop is `not_started` while it is within 400 m of it or > 200 m off the trip's shape (driving there from the depot); a vehicle past its last stop shows the brigade's next trip as `not_started`, one with no trip (after the last trip of the day, or no upcoming stops: about half the fleet at 23:00) is position-only with `delay: null`. zbiorkom never closes some trips (its delay then grows with the clock while the bus stands): standing at the last stop, or standing ≥ 10 min with ≥ 10 min delay (`STUCK_SEC`), ends the trip, otherwise the board shows a ghost departure "now". `/api/fleet/<side>?city=gzm` answers an idle card (`gzmIdleDetail`) for a vehicle on the map that the tracker never saw on a course. Wire = the MZK dialect (seconds, `operator: "GZM"`); ids `gzm:<stop_id>`, `gzm:<trip_id>`, `gzm:<op>_<fleet>` (vehicle/exec; the fleet label alone collides across companies), shapes `gzm:<shape>.<rev6>`. List routes branch on `parseCity(req)` (`?city=gzm`; absent = BB unchanged, unknown = 400, `KB_GZM=0` = 404); id routes branch on the `gzm:` prefix and `/api/trips` splits a mixed batch BEFORE the KB path (a `gzm:` id must never reach upstream). `null` from a `GzmLive` query means "feed loading" (route answers `warming()` = 503 + `Retry-After`), `"unknown"` means not in the feed. Departures/timetables come from the local feed (`stopEvents`) plus the live delay, never an upstream call per stop; connections run RAPTOR over the GZM index only (60 s memo, LRU 256, charged 20 rate-limit tokens: the search is synchronous on the shared loop). `/api/vehicles?city=gzm` gzips its prebuilt body itself, once per body change (~390 KB -> ~48 KB): `next start` compresses pages but leaves route handler responses uncompressed. `/api/gtfs-rt.pb` stays BB-only. Metrorower (`lib/gbfs.ts`, `/api/bikes?city=gzm`, `KB_GZM_GBFS_URL`): nextbike GBFS station_information (1 h) joined with station_status (60 s) server-side, one upstream fetch per minute for everyone, body memoized with ETag + gzip; `components/BikesLayer.tsx` (GZM only, `kb:bikes`, zoom ≥ 14, viewport-culled like StopsLayer) polls only while visible, zoomed in and the tab is shown, and writes a changed count into the existing marker (never `setIcon`).
- **Other zbiorkom cities (`lib/shared/cities.ts`).** `ZB_CITIES` (gzm + 53 api6-open slugs: warsaw, krakow, lodz, wroclaw, poznan, tricity, …; `bielskoBiala` deliberately absent, BB is native) is the ONE registry: server `parseCity` (`?city=<slug>`, unknown = 400, `KB_ZB=0` = 404 except gzm which follows `KB_GZM`), `zbIdCity(id)` = the slug before `:`, client `CITY` (built from it; generic entries poll vehicles every 10 s, operator logo from `public/logos` in the chooser; `color` = the logo's main colour at 4.5:1 under white, pinned by `test/zb-cities.test.ts`, absent = slate: `operatorColor("GZM")` returns the page city's, `setPageCity` writes it into `--color-gzm` for the stop markers; the pill shows the bus/tram glyph, a city logo as a 13 px silhouette is a blob), `isCity`, `cityOfId`, `OTHER_CITIES` (the "Inne miasto" selects), storage keys via `cityKey(base, city)` (`:<slug>` suffix, BB bare). Every such city is a `GzmLive({ slug })` + `startGzmFeed(slug)` (per-slug feed state, zip in `output/gzm/<slug>/gtfs.zip`, ids sanitised by `FeedBuilder.gid()`: `[^A-Za-z0-9_.-]` -> `_`, > 64 chars truncated with a sha1 tail); a `frequencies.txt` template trip (Warsaw metro: 16 templates) becomes one trip per run, `<trip_id>.<start secs>`, at most 20 000 per feed obtained through `getZb(slug)` / `startZb(slug)` (gzm -> `getGzm()`/`startGzm()`), never constructed in a route. Differences from GZM, all deliberate: vehicle key = `<route type>_<vehicle.id>` (`zbKey`; Warsaw/Łódź reuse ids across bus 3 / tram 0, so the url tail KEY_RE is GZM-only), positions URL bbox = the feed's `area` (median-filtered stop extent + 0.05°; all of Poland while the feed parses: the slug alone scopes the answer, so bare positions show before the parse and the trips join on a poll right after it), positions polled ONLY while a request came in within `WATCH_MS` (120 s, `touch()`), no SDIP, no fleet tracker (`/api/fleet*`, `/api/bikes`, `/api/announcements`, `/api/push/news` answer 404), `/api/health` -> `zb` block (informational, never flips `status`). Memory: a feed is 100-230 MB heap (Warsaw the largest), so at most `KB_ZB_RESIDENT` (2) non-gzm cities are resident (LRU `dropZb` = `live.stop()` + `stopGzmFeed`), each dropped after `KB_ZB_IDLE_MIN` (30) min idle by a 60 s unref sweep. Wire stays the GZM dialect (`operator: "GZM"` = "seconds dialect"; the label comes from the registry client-side), shape ids `<slug>:<sanitised shape_id>.<rev6>` (`ZB_SHAPE_ID_RE`, gated by `zbCityOf` so `kb:`/`mzk:` never match the loose charset). Feeds expire on their own schedule (zbiorkom republishes); a slug with a 404 feed just stays `warming()`. Metro (route_type 1, Warsaw M1/M2): zbiorkom sends no metro positions, so `GzmLive.scheduledTracks` places every running metro trip by its timetable (`schedulePosition`, along the shape at the leg's timetable speed, ids `<slug>:1_S<sha1 of trip|date>`, `delay: null`, wire `scheduled: true` = dashed `veh-sched` pill, tooltip and trip note "z rozkładu"); a line any live type-1 record serves is skipped, GZM never schedules.

### Frontend

All components are `"use client"`. `app/page.tsx` → `components/MapShell.tsx`, which is the **single SSR boundary**: `dynamic(import MapApp, { ssr: false })` because Leaflet touches `window` at import time. Never import leaflet/maplibre outside that boundary.

- **City.** `lib/client/city.ts`: a page load shows ONE city, fixed for its life (switching = `location.assign`, so module state keyed at load is safe). `MapShell` resolves it before mounting MapApp: `?city=gzm` or a `gzm:` stop/exec/trip id = GZM, any other app param = BB (old deep links), else the stored `kb:city`, else the picker (shown once; a city from the URL is stored only when nothing is stored yet). BB carries no city marker anywhere: `cityUrl`/`withCity` return BB fetch URLs, URL writes and storage keys unchanged; GZM adds `city=gzm` and suffixes its keys (`stops-gzm` offline copy, `kb:lineFilter:gzm`). GZM polls vehicles every 5 s (the SDIP overlay moves a vehicle every ~5 s), BB every 4 s. A 503 "Data is loading" is shown as `GZM_LOADING` (`isWarming`), never cached, and never wipes a list already on screen. TopBar hides Przewoźnik in GZM (no operator filter there). The tab title is a React `<title>` rendered by MapShell (`app/page.tsx` sets `metadata.title = null`): a `document.title` written from an effect is reset once by Next's late metadata commit right after hydration. An address hit in the search (`onPickPlace`, geocode debounced 350 ms, off after a 404) opens NearbyView around that point (`nearbyPlace`) with a pin.
- `MapApp.tsx` is the single stateful root — no state library; all state flows down as props. It re-renders on every changed 4 s vehicle poll, so children (TopBar, VehicleLayer, StopsLayer, TripLayer, StopView, TripView) are `memo()`-ized and every callback prop must be `useCallback`-stable.
- Data fetching: SWR only for `/api/vehicles` (4 s poll, the app heartbeat; every 2 s before the first answer and while the server has no good upstream poll yet (`timestamp` 0, at most 3 scans); MapShell `preload`s the first request with the city choice so it overlaps MapApp's Leaflet/MapLibre chunk; `vehiclesFetcher` records receive time + `X-Server-Time` in the `vehiclesClock` WeakMap) and `/api/stops` (ETag-revalidated: on focus (at most once a minute), every 15 min, every 20 s while the body says `partial` — a page that lives for days must not keep a list built while one operator's stops were missing; SWR ignores focus events during the first `focusThrottleInterval` after mount, hence the intervals). Everything else is manual `fetch` with AbortController via `lib/client/api`.
- Trip opening uses generation-counter cancellation (`genRef` in MapApp): every async step re-checks `gen !== genRef.current` before setState. New async paths there must do the same or stale trips overwrite newer ones.
- `VectorBaseLayer` (MapLibre GL vector tiles from OpenFreeMap inside Leaflet's tile pane), `StopsLayer` (raw `L.layerGroup`, viewport-culled and diffed, zoom ≥ 14) and `VehicleLayer` (raw `L.layerGroup` diffed by vehicle id; a fleet over `DENSE_FLEET` = 250 vehicles, i.e. GZM, is canvas dots below zoom 13 and pills only within the viewport padded 25 % above it, `lib/client/fleetMarkers.ts`: every DOM pill is its own composited layer and ~720 of them made each pan frame cost Layerize + HitTest) are imperative escape hatches — do not convert them to declarative react-leaflet markers (a `<Marker position>` would snap every animated vehicle back to its raw fix on each poll).
- **Vehicle motion ("Płynny ruch pojazdów").** `lib/client/vehicleAnimator.ts` (one per map, ref-counted) is the ONLY writer of live-vehicle marker positions and arrow angles. It drives the pure dead-reckoning engine `lib/client/vehicleMotion.ts` (along the road shape at the server's cruise speed, capped before the next stop, held while dwelling, smooth catch-up and never visibly driving backwards; tuned with `test/vehicle-motion-sim.test.ts`) from a rAF loop outside React — fleet at a zoom-scaled rate, the tracked bus every frame, paused only while a zoom animation runs (a frame gate, never a sticky flag) and while the tab is hidden. Fleet shapes come from `/api/shapes` (`lib/client/shapes.ts`) at zoom ≥ 13 in view. The per-browser switch is `lib/client/smoothMotion.ts` (`kb:smoothMotion`, an early feature: off unless the user opts in); off = passthrough (raw fixes + the 0.9 s CSS glide). `VehicleLayer` ingests every poll even while hidden so tracks stay warm.
- `VehicleLayer` hides its markers while a trip is open; `TripLayer` draws the tracked vehicle itself, matched from the poll by `vehicle.id === trip.execId`, as an animator view on the SAME track as the fleet marker (no jump on open/close). It overrides the track's shape with the drawn route only when that isn't the fleet shape (`trip.shapeId !== vehicle.shape`). KB/MZK trips and connection legs draw server-stored shapes; browser OSRM (`fetchRoute`) is only the fallback while a shape is still `pending`.
- Deep links: view state lives in the URL (`?stop=`, `?exec=`, `?trip=`, `?lines=`, `?map=` — codec in `lib/client/urlState.ts`) via the **plain History API, never `next/navigation`** (`useSearchParams` would subscribe the whole map tree to every `moveend` replaceState). MapApp's single sync effect is the only URL writer; `popstate` is close-only (Android back closes sheets, state stays authoritative). `exec=` and `trip=` are separate params because the two trip-ID spaces can't be told apart heuristically.
- **Line view.** A line hit in the search opens `LineView` (bottom of the sheet stack like NearbyView, counted as an overlay in the URL sync, no URL param): today's patterns from `/api/line`, a stop's departures by hour, the "Tylko ta linia na mapie" filter chip (the line filter moved here from the search row). Shared chip classes are `CHIP`/`CHIP_ON`/`CHIP_OFF`/`chip()` in `components/ui.tsx`.
- **Theme.** Dark tokens in `@theme`, light overrides under `:root[data-theme="light"]` (`app/globals.css`). The inline script in `app/layout.tsx` sets `data-theme` before first paint from `kb:theme` (absent = system, followed live) and owns its own first `<meta id="kb-theme-color">` (editing Next's theme-color tags makes React re-insert them at hydration); `lib/client/theme.ts` backs the "Motyw" switch. Hover / fill overlays use `bg-tint/N` (white on dark, black on light), never `bg-white/N`. `/brygady` stays dark (its charts use fixed colours). The default map style follows the theme until the user picks one.
- Announcements ("Utrudnienia"): `lib/client/announcements.ts` is a module-level `useSyncExternalStore` store (same pattern as `favorites.ts`) polling `/api/announcements` (city-aware: `cityUrl`, seen key `kb:annSeen` + `:gzm`) every 15 min; unread = upstream `hash` vs the seen hash in localStorage. Never wire it into the 4 s poll cycle. Server side `lib/announcements.ts` `fetchAnnouncements(city)` is the ONE list builder (BB = KB feed + MZK messages, GZM = `lib/gzm-news.ts`, a 15-min memoized scrape of the ZTM news page `KB_GZM_NEWS_URL`, pure parser pinned by `test/gzm-news.test.ts`). "Powiadamiaj o utrudnieniach" = `lib/push-news.ts` (`/api/push/news`): ≤ 500 subscriptions with their cities in `KB_PUSH_DIR/news.v1.json`, a 15-min tick armed only while someone is subscribed pushes the headline of each new `operator:id:rev` key (the first list of a city is only recorded; seen keys are a bounded insertion-ordered set, so a leg that fails one tick does not re-notify); the page re-POSTs its subscription on load (`kb:newsPush` + `:gzm`).
- PWA updates: `public/sw.js` deliberately does **not** `skipWaiting()` on install — a new SW waits until `PwaRegister`'s toast posts `SKIP_WAITING`, and the reload on `controllerchange` only fires after explicit accept (`clients.claim()` fires it on first install too — an unconditional reload would refresh every new visitor).

### Single-process assumption

Poller singleton, rate-limit buckets, stop-directions cache and the road-shape store worker are all in-memory state in one long-lived Node process (the shape store file is additionally lock-guarded: a second process sharing `output/` stays read-only). Serverless or multi-instance deployment breaks rate limiting and multiplies upstream load. The singleton lives on `globalThis` under `Symbol.for("kb-gtfs.poller-singleton")` specifically to survive dev-mode HMR — never construct `LivePoller`/`KbApi` directly; go through `lib/poller-singleton.ts`.

## Gotchas

- **Python parity is intentional.** `pyTruthy`, `parseIntStrict`, etc. in `lib/kb-api.ts` replicate Python truthiness/`int()` semantics and are used across lib and routes; do not "simplify" them to JS truthiness. Likewise "JSON parse errors are not retried" is parity, not an oversight. An empty `{}` from a passthrough route means "upstream returned nothing" (e.g. vehicle not departed yet), not an error.
- **404 cache must not re-stamp.** In `lib/poller.ts` a candidate skipped due to a fresh cached 404 keeps its original timestamp — scan interval (180 s) < 404 cache (240 s), so re-stamping would slide the TTL forever and permanently hide a late-dispatched bus.
- **Ghost vehicles.** Upstream never 404s dead trips; it keeps returning the last position. Filtering relies on movement anchors (`anchorLat/anchorLon/lastMovedAt`, 15 m epsilon), staleness (frozen 300 s with no delay estimate), and `pruneDead`. The internal `positions` Map may contain vehicles that `liveVehicles()`/`toJson()` deliberately hide.
- **Time math is agency-local.** All schedule math uses seconds-since-midnight in Europe/Warsaw via `Intl` (`nowSecs()`), not server-local time, with ±43200 s midnight wrap — servers run UTC.
- **Upstream data quirks.** Positions can be bogus (0,0) — rejected via hardcoded SERVICE_AREA bbox (lat 48.8–50.5, lon 18.0–20.5). Stop coords arrive as micro-degrees (÷1e6). `trip_execution_id` is base64-encoded (`b64ExecId`) before hitting upstream URLs. `/api/departures?places=` silently caps the response at **6 boards per request** (extra stops are just absent) — hence `KB_BATCH_SIZE=6`; a board absent from the reply means truncation, not an empty stop (empty stops still get a board with empty rows), so the poller must not stamp the empty-cache for it.
- **Two stop ID spaces.** `Stop.urlId` (URL designator, may contain `:`) vs numeric `internalId`/`stopId`. On the frontend, trip time entries match `time.designator → Stop.id` and `time.place_id → Stop.designator` — not interchangeable.
- **Vehicle icons key on line/color/operator/hasHeading — never the heading.** The animator rotates the `.veh-arrow` element in place (unwrapped angles so CSS never spins the long way); `setIcon` rewrites the DOM and replays the pop animation, so putting the bearing back into an icon key makes markers blink on every turn. `TripLayer` keeps an `eslint-disable react-hooks/exhaustive-deps` on its marker effect on purpose (raw live coords only seed a new marker).
- **Motion clocks.** The engine runs on one local monotonic clock (`performance.now()`); server epoch seconds (`fix_at`) are mapped via the `X-Server-Time` offset. Never feed `Date.now()` or the KB `timestamp`/`updated_at` (= our fetch time) in as a fix time.
- **New passthrough routes must keep the security trio:** `isValidId`/`isValidDate` input validation (blocks URL injection into upstream paths), `upstreamError()` (generic 502, never leaks upstream details), and the rate-limit gate. `/api/trip_execution` skips `isValidId` deliberately because the id is base64-encoded first.
- Route handlers use the Next 15+ async params shape: `ctx.params` is a Promise and must be awaited. All API routes set `dynamic = "force-dynamic"` and `runtime = "nodejs"`.
- `output/` is generated (GTFS feeds, logs), gitignored, and eslint-ignored — not stray files.
- 0 vehicles after midnight is normal; buses run ~4:30–22:00.
