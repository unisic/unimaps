# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

**Unimaps** (repo `unisic/unimaps`, GPL-3.0-or-later), a live transit map for Bielsko-Biała (Komunikacja Beskidzka + MZK), Metropolia GZM and 53 other zbiorkom cities: **one Rust process** (`backend/`, binary `unimaps`, hyper 1 + tokio, edition 2024) serves the JSON API, a GTFS-RT VehiclePositions protobuf feed and the Leaflet map UI (Svelte 5 + Vite, TypeScript strict, a static build in `out/`), and runs the live pollers in-process. Vite is a build tool and the dev server only; nothing of it runs in production. The KB upstream is `https://komunikacjabeskidzka.kiedyprzyjedzie.pl` (KiedyPrzyjedzie). App identity is Unimaps, but the `KB_*` env vars, `kb:*` storage keys and the `kb-output` volume keep their names on purpose (renaming breaks deployments and user state). `backend/src/` is a deliberate behavioral-parity port of the former Node backend, itself a port of a Python codebase (see Gotchas); each module's doc comment names the TS file it replaced (`git show 075826c:<path>`, the last commit with the Node backend). README.md (English) is a short overview (run, main endpoints, data sources); `.env.example` lists every env var except compose's `KB_HOST_PORT` (see below).

## Commands

```bash
npm run dev          # scripts/dev.mjs: `cargo run` (debug) on 127.0.0.1:KB_API_PORT (8081) with an empty static dir,
                     #   beside Vite's dev server on HOST:PORT (0.0.0.0:8080, HMR), which proxies /api to it (xfwd);
                     #   either one exiting stops both; a Rust edit needs a restart (no watch)
                     #   PORT=8082 npm run dev when 8080 is taken (Steam's steamwebhelper listens on 127.0.0.1:8080)
npm run build        # vite build (app/*.html -> out/), precompress out/ (.br/.gz, scripts/compress-static.mjs)
npm start            # cargo run --release: API + out/ (KB_STATIC_DIR, default <cwd>/out)
npm run lint         # eslint .
npm run typecheck    # svelte-check: tsc over .ts plus .svelte (types and a11y)
npm test             # node --import tsx --test "test/**/*.test.ts": client and lib/shared tests only
npm run build:gtfs -- --date 2026-07-05   # = `unimaps build-gtfs` (logic in backend/src/gtfs_builder.rs); reads no .env file
                     #   flags: --date YYYY-MM-DD, --out DIR, --concurrency N, --no-zip, --single-day
cd backend && cargo fmt --check && cargo clippy --all-targets -- -D warnings && cargo test
```

Verification is `npm run typecheck` + `npm run lint` + `npm test` + the Rust checks + exercising the running app (`/api/health` shows status/scan counters). CI (`.github/workflows/ci.yml`): job `check` runs the first three plus `npm run build`, job `rust` the Rust checks (`--locked`), job `docker` a `docker build`, job `audit` (also daily) `npm audit --omit=dev --audit-level=high` and `cargo audit`. CI must never run `build:gtfs` (hits the live upstream). Tests in `backend/tests/` (ports of the former TS tests, real captured data in `test/fixtures/`, golden vectors in `backend/tests/vectors/`) **pin Python-parity semantics**: a failing parity test means a regression in the backend, never "fix" the expectation. `scripts/http-contract.test.ts` pins the HTTP front from outside (needs `out/` and live upstreams, so not in `npm test`/CI): `BASE_URL=http://127.0.0.1:8080 node --import tsx --test scripts/http-contract.test.ts`.

**Backend.** `backend/src/main.rs`: `unimaps` (or `unimaps serve`) loads the `.env` files, listens on HOST:PORT (at most 1024 connections, 10 s to send the headers), serves `out/` and the API and runs `boot()` (BB pollers, GZM, push stores); `unimaps healthcheck` (the image/compose healthcheck) exits 0 when `/api/health` answers 2xx; `unimaps build-gtfs` is the GTFS builder CLI. SIGTERM/SIGINT give the pollers 5 s (`STOP_GRACE`) to stop and flush their stores, then exit 0. The Docker image is the static musl binary plus `out/` on alpine, nothing else (rustls reads the base image's CA bundle, jiff bundles its own tzdb).

**Logic that exists twice.** The browser keeps its own copy of `lib/shared/*.ts` (`alerts`, `cities`, `departures`, `detours`, `fleet`, `gzm-stop-key`, `polyline`); the server has it in `backend/src/shared/*.rs`. A logic change in `lib/shared/*.ts` that the server also implements must be made in `backend/src/shared/*` too, with the golden vectors in `backend/tests/vectors/` updated by hand (their generator went with the Node backend); `test/rust-vectors.test.ts` reads the same vectors through the TS and pins that side. `lib/shared/cities.json`, `lib/shared/detours.json`, `lib/mzk-fleet.json` and `lib/phototrans.json` are compiled into the binary (`include_str!`; the Dockerfile copies them into the rust stage): an edit needs a rebuild.

Default port is **8080** everywhere (dev, start, Dockerfile, compose), not 3000; bind address `HOST` (default `0.0.0.0`; not `HOSTNAME`, which shells and Docker set to the machine name). In dev 8080 is Vite and the API listens on `KB_API_PORT` (8081). Docker: `docker compose up -d --build`; the published host port is `KB_HOST_PORT` (default 8080, read only by `compose.yaml`; `PORT` inside the container is pinned to 8080, never change it to move the host port); healthchecks run `/app/unimaps healthcheck`, which hits `/api/health`.

Config is via `KB_*` env vars (see `.env.example`), all optional. `backend/src/config.rs` reads each one once, on first use (`LazyLock`, after the `.env` files are loaded): changing one requires a process restart. `load_env_files()` (`backend/src/main.rs`) loads `.env.<mode>.local`, `.env.local`, `.env.<mode>`, `.env`: a variable already set always wins; mode = `NODE_ENV` when set (`npm run dev` sets `development`), else `production` for a release build and `development` for a debug one. `KB_LOG_LEVEL=info|warn|error` (`backend/src/logger.rs`).

## Architecture

### Backend data flow

```
backend/src/main.rs  boot()  (backend/src/http.rs; also GZM + push alerts/news)
  └─> poller_singleton::bb().start_poller()   (idempotent; one static Bb)
        └─> poller.rs LivePoller              (background loop, in-memory positions map)
              └─> kb_api.rs KbApi             (reqwest, concurrency KB_CONCURRENCY 40, retries)
                    └─> upstream API
```

- **HTTP layer.** `backend/src/http.rs` matches `/api/*` with `match_route` (`backend/src/api/mod.rs`, one module per route under `backend/src/api/`, `[name]` segments as params) and runs it through `dispatch_owned` on its own task (a panic = 500): HEAD = GET without a body, OPTIONS = 204 + `Allow`, 405 for other methods, 404 JSON for an unknown path, body capped at 64 KB (413), `x-forwarded-for` set from the socket when absent (`client_ip()`, `backend/src/rate_limit.rs`, takes the last entry). Any path ending in `/` gets a 308 to the bare path (leading slashes/backslashes collapsed: no off-site redirect). Everything else goes to `backend/src/static_files.rs` (the whole build read into memory at start, `.br`/`.gz` siblings by `Accept-Encoding`, weak ETag, Vite's hashed `/assets/` immutable, html `no-cache`, a miss = `404.html` with 404; a missing `out/` logs `no static build at …` and every page answers a bare 404 while the API runs). In dev Vite serves the pages and proxies `^/api(?:[/?]|$)` (`vite.config.ts`). The server compresses only `/api/vehicles` and `/api/stops` (every city): `prebuilt_json` (`backend/src/api_helpers.rs`) gzips each prebuilt body once per body change when the client accepts gzip (GZM vehicles ~390 KB -> ~48 KB); pages are precompressed at build.
- Routes under `backend/src/api/` read poller snapshots: `/api/vehicles` (`to_json()`), `/api/gtfs-rt.pb` (`to_protobuf()`, a hand-written proto2 writer in `backend/src/gtfs_rt.rs`), `/api/stops`, `/api/health`. The BB routes that read poller state **also** await `bb().start_poller()` as a lazy fallback, so the poller starts even without `boot()`.
- `/api/geocode?q=` (address search for a connection from or to a point, `from=`/`to=geo:LAT,LON` = every pole within `walk` m, 200-1500, default 800, as access / egress walk; the client keeps the choice in `kb:walkMax`) proxies Photon (`KB_GEOCODER_URL`, `off` = 404) inside a per-city bbox: memo 1000 queries / 24 h, at most 4 requests in flight for all cities (more = 429), one client request per typing pause.
- `/api/connections` takes `arriveBy=true` (needs `time`, else 400): `time` becomes the latest arrival and the answer is the `limit` latest-departing connections that make it, same day only (no next-day fallback). `avoid=` line names / `avoidTypes=` GTFS route types (zbiorkom cities only), at most 20 each, malformed = 400; `sortBy=transfers|walk` (walk weighs foot transfers x3). Today's search boards running trips at their live times (`live` = `bb_live_delay()` / GZM `byTrip`): `adjust_table` (`backend/src/router.rs`) shifts each live trip, a late trip stays in its route while the route stays FIFO, an overtaker gets a one-trip route; legs keep timetable times plus `delaySec`. Cost O(trip instances of the day) per search, ~+40 ms on GZM's ~230 ms. Searches run one at a time on a blocking thread (`SEARCH_TURN`, `backend/src/api/connections.rs`) inside a process-wide time budget (`allow_search`/`charge_search`, `backend/src/rate_limit.rs`: 250 ms/s, 200 ms burst, charged the measured duration) that also comes out of the client's own bucket at 1 token per 2.5 ms (one IP holds at most ~100 ms/s); overdrawn = 429, which `ConnectionsDialog` shows as "zajęta".
- `/api/line?name=[&op=KB|MZK][&date=]` (`?city=gzm` = GZM) feeds the line view: `line_timetable()` (`backend/src/router.rs`) over the BB router index or the GZM feed's, the 12 busiest stop patterns active on the date with each trip's departure per stop in minutes from that midnight. O(trips) scan per request, `public, max-age=3600`, rate-limited; no index yet = `warming()`.
- `/api/push` (`backend/src/push_alerts.rs` + `backend/src/web_push.rs`: VAPID ES256 + RFC 8291 aes128gcm on the `p256`/`aes-gcm`/`hkdf` crates, pinned by the RFC test vector) fires a "Powiadom mnie" alert as a web push with the app closed: a browser POSTs `{subscription, alert}` (endpoint allowlisted to the push services, it is an outbound POST target), a 30 s tick armed only while alerts are pending reads each alerted stop's board (`stop_board()`, `backend/src/stop_board.rs`, the departures route's own micro-cached board; GZM from the local feed) and pushes what the shared `alert_action` (`backend/src/shared/alerts.rs` = `lib/shared/alerts.ts`) decides. At most 300 alerts, 6 per subscription, each dropped at `until`; 404/410 from the push service drops the subscription. VAPID pair + alerts in `KB_PUSH_DIR` (`output/push`, 0600); a lost `vapid.json` orphans every subscription. The page watcher still fires too (same tag, one notification).
- Passthrough routes (`/api/trip/[tripId]`, `/api/trip_execution`, `/api/stop/[designator]/departures|timetable`) proxy the upstream directly, gated by `backend/src/rate_limit.rs` (in-memory per-IP token bucket) and `backend/src/api_helpers.rs` validation.
- Poller rhythm (defaults, `backend/src/config.rs`): full scan of all ~956 stops every 90 s, smart incremental scan every 30 s, position refresh of active vehicles every 10 s (+ work time; upstream itself only moves a KB position every ~6–18 s). MZK (`backend/src/mzk_poller.rs`) polls its whole fleet every 5 s. It discovers `trip_execution_id`s from departures (the only way to get positions: they live in a different ID space than static `trip_id`). The loop runs under `supervise()`: a panic restarts it with capped backoff (`loopRestarts` in health). The stop list reloads daily (`KB_STOPS_RELOAD_SEC`) with an atomic map swap; a failed (or empty) reload keeps the old list. The MZK stop list follows the same rule (`MzkPoller::load_stops`) and is additionally reloaded, at most every 10 min, when a running course references an unknown stop symbol: upstream re-versions its stop data (2026-09-30), so a list loaded once at boot goes stale.
- `/api/health` returns `"degraded"` + HTTP 503 (flips Docker healthchecks) when the scan loop stalls or upstream contact exceeds `KB_HEALTH_STALE_SEC` (1200 s > the 600 s overnight all-cached window). Deliberately no vehicle-count condition: 0 at night is normal.
- `backend/src/gtfs_refresh.rs` (armed from `start_poller()`, wired in `backend/src/poller_singleton.rs`) rebuilds the GTFS feed in-process: immediately when `output/gtfs` is missing (fresh Docker volume), else daily after `KB_GTFS_BUILD_HOUR` Warsaw time, then invalidates the stop-directions/lines caches. The builder logic lives in `backend/src/gtfs_builder.rs`; `unimaps build-gtfs` is just the CLI. Compose mounts the named volume `kb-output:/app/output`.
- `backend/src/shape_store.rs` is the **road-shape store**: road-following geometry for KB stop patterns (`backend/src/shape_patterns.rs`: keyed by stop ids + applied detour, routed server-side through OSRM by `backend/src/osrm.rs`, one throttled worker, ≥1 s between requests on the public demo host) and MZK variants (operator API, `backend/src/mzk_shape.rs`). Persisted to `output/shapes/route-shapes.v1.json` (atomic sync writes + `.bak`, lock file = single writer; a non-owner is read-only), refreshed gradually (one entry per 2 min, road shapes after `KB_SHAPES_MAX_AGE_DAYS`), seeded from the GTFS patterns after start and every nightly build. A new pattern gets a straight entry at once; a road entry is never downgraded; OSRM failures pause the worker (circuit breaker) and never touch `/api/health` status. `/api/shapes?ids=` only reads the store (never routes/fetches), ids are `<key>.<rev6>` so exact hits are `immutable`. GZM bus and trolleybus shapes (zbiorkom's are sparse: line 27 = 411 points over 38 km, corners cut through buildings) are snapped by `backend/src/gzm_match.rs`: OSRM `/match` when a trip of the shape is opened (`/api/trip/<id>` and exec, never the `/api/trips` batch), Douglas-Peucker 10 m first, chunks of 10 points on the public host, an implausible chunk (> 1.3 x the trace + 50 m, or a point > 60 m off) keeps its raw points; one shared `OSRM_PACE` with the shape store, so both stay at 1 req/s together (line 27: 19 requests, ~20 s on the public host). One OSRM request at a time, each for the route opened or watched last (a `near` poll or a new open moves its job to the front between two requests, the older match resumes where it stopped; at most 20 queued), every opened shape with the same geometry joins the running job. Within a job the chunks crossing the focus box go first (opening a vehicle's trip: 800 m around it; then the rider's map, sent as `/api/shapes?ids=<id>&near=s,w,n,e`, which only re-aims a running job and never starts one) and are published at once as a `src: "partial"` shape (the matched part on the simplified raw rest, an overlay in `GzmShapes` with its own rev, never persisted), so the road shows in view after 1-2 requests while the rest follows. Stored in `output/gzm/matched-shapes.v1.json` keyed by `raw_key` (sha1 of the raw polyline, 16 hex: 4161 shapes share 2642 geometries, so a twin is instant), applied by every feed build, pruned when a feed is installed; a match gives the shape a new rev (new wire id). While it runs the trip answer carries `shape_matching: true` and MapApp polls `/api/shapes?ids=<current id>&near=<view padded 25 %>` (`fetchNewerShape`, no-store, `If-None-Match: "<id>"` = a bodiless 304 while unchanged, every 1 s, at most 100 per stage) and swaps the route on each newer id, polling on while it is `partial`; the 30 s live refresh stays the fallback. Trams and the other zbiorkom cities stay raw.
- **Stop merging (KB + MZK).** `merge_stops(kb, mzk, mzk_dirs)` (`backend/src/stop_merge.rs`) is a pure, order-independent global assignment (Hungarian per connected component, max cardinality first): eligible = ≤ 35 m, or ≤ 120 m with matching cleaned names; a pair whose travel directions are opposite (KB `dirs` from GTFS vs MZK bearings learned by `backend/src/mzk_stop_dirs.rs` from the stop ORDER of running courses, persisted to `output/mzk-stop-dirs.v1.json`, dropped when a stop moves/vanishes) is eligible only ≤ 12 m. The learned MZK bearings steer the pairing ONLY: they never reach the wire (arrows stay a KB/GTFS feature). A bus station (`is_station`) pairs only ≤ `MERGE_HUB_M` = 35 m and fans its departures/timetable out to the other same-name MZK stops in that radius (`mzkSymbols`, primary first; Czechowice-Dz. D.A. = 2366 + 2367). Those extras are folded into the hub: no entry of their own (one marker per station), their symbols alias to it in both lookups (server `index_merged_stops`, client `byDesig`). Its cleaned name is the bare `DWORZEC`, which matches every MZK `<street> Dworzec`, so a wider radius pulls street stops in: Bielsko-Biała D.A. is KB-only (MZK 343/341/342/264/469 at 89-183 m are stops of their own); those stops stay MZK-only entries with their own position (MZK trip timelines are drawn at the resolved stop's coordinates). `backend/src/merged_stops.rs` is the ONE memoized source (`Bb::merged_stops_view()` in `backend/src/poller_singleton.rs`, keyed on input identity) for `/api/stops` (ETag/304; `no-cache` + `partial: true` while one operator's list is missing), the departures/timetable routes and `/api/health`: never re-merge ad hoc. The departures/timetable routes answer `warnings: ["kb"|"mzk"]` (and the timetable `no-store`) when an upstream fetch failed: a failed fetch is not "no departures". `MzkApi` caches `fetch_realtime` 5 s / `fetch_atomic_schedule` 15 min (in-flight deduped, failures never cached). Tests pin real captured data (`test/fixtures/stop-merge-live.json`, read by `backend/tests/stop_merge.rs`).
- The pollers attach route info per vehicle (`backend/src/route_info.rs`, isolated with `catch_unwind` so it can never abort a refresh): shape key, `fixAt` (KB has no upstream fix time: midpoint of the poll window that saw the change; MZK `lastPingDate`), along-route `distM`, and a cruise `speed` taken only from consecutive moving fixes outside stop zones. `vehicle_extras()` puts them on the wire (`shape`, `dist_m`, `fix_at`, `next_stop_seq`, `speed`, plus `sched_speed`: the timetable pace around `dist_m`, `sched_speed()`, which the client blends 50/50 with `speed`); `vehicle_to_json` (`backend/src/vehicle.rs`, the Python port) stays untouched. `/api/vehicles` also sends `X-Server-Time` (a header, so unchanged payloads still dedupe in the client's `swr()`). Trip responses carry `shape_id` + `shape_status` (`road|pending|none`); `/api/connections` legs carry `shape_id`.
- **KB delay = upstream's value only while its stop index is trustworthy.** Upstream registers a stop only when one of its 6–18 s GPS samples lands in the stop zone; a bus that passes stops without slowing is never registered, `vehicle_trip_index`/`next_departure_index` stall and `estimates[0]` is clamped to "now" for the stale stop, so `parse_position`'s delay (`estimates[0] − plan(next stop)`, still the untouched Python-parity formula) grows +1 min/min (+5 → +11 on a bus that is on time). `backend/src/kb_progress.rs` (pure, straight stop-to-stop geometry, called from `LivePoller::attach_progress` on EVERY poll before `attach_route_info`) places the bus monotonically (upstream's last registered stop = hard lower bound, so the outbound leg of a loop can't steal a return-leg fix) and, only when the bus is > 120 m beyond the stop upstream calls next, overwrites the delay with the schedule deviation at the real position. `delay_up` keeps the raw value: `is_feed_stale()` MUST test it (a GPS delay must not hide a frozen feed). While stale, `/api/vehicles` also carries `delay_src` (`gps`|`gps-held`|`unknown` = delay withheld/null) and `geo_seq` (GPS index of the last passed stop); the client prefers `geo_seq` over `current_stop_sequence` as the `findActiveStop` hint (a stale hint puts a bus on the OUTBOUND leg of a loop) and `attach_route_info` feeds the GPS indices to `kb_dist_along`. In sync nothing changes. `KB_GPS_DELAY=0` disables it; `/api/health` → `stale_index` counts affected vehicles. Cold start (restart) mid-loop with a stale index is ambiguous and falls back to upstream's value.
- **Loop / twin-stop trips.** Out-and-back patterns (line 120 Szczyrk Biła, 37 % of KB trips) use *twin* stops (opposite sides of one road, 14–50 m apart, km apart along the route) and upstream's stop index can freeze for minutes. `kb_dist_along` (`backend/src/route_info.rs`) is continuity-first (previous `dist_m` as hint, window widened by the poll gap via `kb_ahead_m`, then the vti window fed with the GPS indices, then a strict search); `findActiveStop` (`lib/client/geo.ts`) honours `at_stop` + the hint within 90 m and prefers, among near poles, the one closest to the hint index; TripView reads `dist_m` against the shape chainage (`lib/shared/trip-progress.ts`, pure).
- **MZK "course not begun".** For a course that has not started OnTime sends a placeholder: `delaySec = max(-60, now − first scheduled departure)` and every `plannedDeparture = scheduled + that`. `is_mzk_not_started()` (`backend/src/mzk_state.rs`) classifies it once (orderInCourse 0 and lastStopOrderNo null, or 0 with reachedMeters < 30; bus > 400 m from the first stop = started); the poller publishes `delay: null` + `not_started` (via `vehicle_extras`), live trips carry no per-stop estimates (none at all in publicly cached static trips), departure rows get the earliest possible time + `not_started`, the fleet tracker (`backend/src/fleet_tracker/`) neither counts nor archives such courses. A `not_started` row/vehicle must never yield a delay from ANY source (`resolveTiming` enforces it).
- **Departures board.** Two time dialects (KB relative "N min" strings floored, `time: null` + `at_stop`, far-off rows as "HH:MM", `time_diff` in MINUTES; MZK absolute instants + vehicle delay in SECONDS). The server normalises rows to epoch seconds (`backend/src/shared/departures.rs` = `lib/shared/departures.ts`: `plan_ts`, `eta_ts`, `delay_sec`, `row_key`, `server_ts`), the client resolves ONE canonical ETA per row (`resolveTiming`) and uses it for both the label and the order (printed minute → line → plan → key; rows > 60 s past due are hidden). StopView polls via `lib/client/live-poll.ts` (10 s ±15 %, 12 s per-request timeout, backoff, catch-up on visibility/pageshow/focus/online, watchdog, never two requests in flight; a failing refresh never wipes the list, a stale stamp appears after 45 s). The route builds each board behind a 4 s micro-cache (`backend/src/departures_board_cache.rs`, keyed by merged-stop identity) and answers 502 when every upstream leg failed.
- **Whole-stop board.** `/api/stop/<id>/departures?all=1` (anything else = 400) lists every same-name pole nearby, each row tagged with `pole`; every answer carries `poles` when the stop has more than one pole, and that turns on StopView's "Cały przystanek" chip (Odjazdy tab only, no timetable fill or earlier/later buttons in that mode). GZM: `gzm_stop_key` groups within 600 m, at most 12, `pole` = post number, served from the local feed. BB: `stop_group()` (`backend/src/stop_board.rs`, same merged name within 500 m, at most 6) and `group_board()` = one micro-cached `stop_board()` per pole, one rate-limit token per pole, `pole` = compass direction from `dirs` (only when a pole has exactly one bearing).
- **Request stops ("na żądanie").** A stop's `onRequest`: MZK's own flag, KB = the name ends in "NŻ" (`format_kb_stops`, KB has no flag; merged = OR), zbiorkom = most of the stop's calls have `pickup_type`/`drop_off_type` 2 or 3 (`GzmFeed` stops body, per stop, not per call). StopView's header and TripView's stop rows show it as `RequestStopTag` (amber pill, `components/ui/RequestStopTag.svelte`) and drop the name's "NŻ" tail (`withoutRequestTail`).
- `backend/src/stop_directions.rs` derives stop direction arrows from pre-built GTFS files in `output/gtfs/`; missing files silently yield no arrows. Cached per process until `invalidate_stop_directions()`/`invalidate_lines()` (called after a rebuild); `/api/stops` re-serializes when either the stop-list or the directions-map identity changes (see "Stop merging").

- **Metropolia GZM (second city).** `backend/src/gzm_feed.rs` (zbiorkom GZM GTFS zip in `output/gzm/gtfs.zip`, streamed parse into one immutable `GzmFeed`: stops body + ETag, lines, trips with dates (calls as columns, `call_columns` in `backend/src/router.rs`: `stop_ids`/`seqs` shared by every trip with the same calls, own `arr`/`dep`, one array when equal; GZM 116 -> 40 MB), shapes, a `RouterIndex` from `build_router_index`) and `backend/src/gzm/` (`GzmLive`, one per city in `gzm/registry.rs`, started from `boot()` and lazily by every GZM route branch via `start_gzm()`). It is isolated from `start_poller()`: a GZM failure never touches BB data, and the `/api/health` → `gzm` block never flips `status`. zbiorkom positions are polled every 10 s phased 3 s after zbiorkom's own 10 s grid (it was 20 s until 2026-10-28; the first fix of a vehicle sits mid-window, `ts - 5`); SDIP (`planner/v`, JSESSIONID cookie, a whole-list snapshot every 5 s, visible ~1.9 s past each epoch 5 s mark) overlays positions 2.5 s past every 5 s step only while a GZM request came in within 120 s, with a 5 min pause after 3 failures; its dated fix wins for as long as SDIP reports the vehicle (zbiorkom serves the same positions 5-60 s later, so a time comparison hands a standing bus back to an older spot), a vehicle missing from one SDIP list keeps its sample. A record joins a trip ONLY when every upcoming (seq, scheduled departure) pair matches a trip of its line active today or yesterday (exact first, then within `MATCH_SLACK_SEC` = 30 s: Tczew's live calls run 5 s off zbiorkom's own GTFS), brigade breaks ties; a bus whose next call is the first stop is `not_started` while it is within 400 m of it or > 200 m off the trip's shape (driving there from the depot); a vehicle past its last stop shows the brigade's next trip as `not_started`, one with no trip (after the last trip of the day, or no upcoming stops: about half the fleet at 23:00) is position-only with `delay: null`. zbiorkom never closes some trips (its delay then grows with the clock while the bus stands): standing at the last stop, or standing ≥ 10 min with ≥ 10 min delay (`STUCK_SEC`), ends the trip, otherwise the board shows a ghost departure "now". `/api/fleet/<side>?city=gzm` answers an idle card (`gzm_idle_detail`, `backend/src/gzm_fleet.rs`) for a vehicle on the map that the tracker never saw on a course. Wire = the MZK dialect (seconds, `operator: "GZM"`); ids `gzm:<stop_id>`, `gzm:<trip_id>`, `gzm:<op>_<fleet>` (vehicle/exec; the fleet label alone collides across companies), shapes `gzm:<shape>.<rev6>`. List routes branch on `parse_city()` (`backend/src/api_helpers.rs`; `?city=gzm`; absent = BB unchanged, unknown = 400, `KB_GZM=0` = 404); id routes branch on the `gzm:` prefix and `/api/trips` splits a mixed batch BEFORE the KB path (a `gzm:` id must never reach upstream). `Lookup::Loading` from a `GzmLive` query (`backend/src/gzm/parse.rs`) means "feed loading" (route answers `warming()` = 503 + `Retry-After`), `Lookup::Unknown` means not in the feed. Departures/timetables come from the local feed (`stop_events`) plus the live delay, never an upstream call per stop; connections run RAPTOR over the GZM index only (60 s memo, LRU 256, charged 20 rate-limit tokens: GZM's feed is far larger, ~22k trips a day). `/api/gtfs-rt.pb` stays BB-only.
- **Other zbiorkom cities (`lib/shared/cities.json`).** `ZB_CITIES` (gzm + 53 api6-open slugs: warsaw, krakow, lodz, wroclaw, poznan, tricity, …; `bielskoBiala` deliberately absent, BB is native) is the ONE registry, read by `lib/shared/cities.ts` and `backend/src/shared/cities.rs`: server `parse_city` (`?city=<slug>`, unknown = 400, `KB_ZB=0` = 404 except gzm which follows `KB_GZM`), `zb_city_of(id)` = the slug before `:`, client `CITY` (built from it; generic entries poll vehicles every 10 s, operator logo from `public/logos` in the chooser; `color` = the logo's main colour at 4.5:1 under white, pinned by `test/zb-cities.test.ts`, absent = slate; `lineColors` overrides single lines, Warsaw M1/M2 from the feed's route_color: `operatorColor("GZM", line)` returns the page city's, `setPageCity` writes it into `--color-gzm` for the stop markers; the pill shows the bus/tram glyph, a city logo as a 13 px silhouette is a blob), `isCity`, `cityOfId`, `OTHER_CITIES` (the "Inne miasto" selects), storage keys via `cityKey(base, city)` (`:<slug>` suffix, BB bare). Every such city is a `GzmLive` + `start_gzm_feed(slug)` (`backend/src/gzm_feed.rs`, per-slug feed state, zip in `output/gzm/<slug>/gtfs.zip`, ids sanitised by `gid()`: `[^A-Za-z0-9_.-]` -> `_`, > 64 chars truncated with a sha1 tail); a `frequencies.txt` template trip (Warsaw metro: 16 templates) becomes one trip per run, `<trip_id>.<start secs>`, at most 20 000 per feed, obtained through `get_zb(slug)` / `start_zb(slug)` (gzm -> `get_gzm()`/`start_gzm()`), never constructed in a route. Differences from GZM, all deliberate: vehicle key = `<route type>_<vehicle.id>` (`zb_key`; Warsaw/Łódź reuse ids across bus 3 / tram 0, so the url tail `KEY_RE` is GZM-only), positions URL bbox = the feed's `area` (median-filtered stop extent + 0.05°; all of Poland while the feed parses: the slug alone scopes the answer, so bare positions show before the parse and the trips join on a poll right after it), positions polled ONLY while a request came in within `WATCH_MS` (120 s, `touch()`), no SDIP, no fleet tracker (`/api/fleet*`, `/api/announcements`, `/api/push/news` answer 404), `/api/health` -> `zb` block (informational, never flips `status`). Memory: a feed is 25-60 MB (Warsaw the largest; measured on the Node backend, 2026-10-31), so at most `KB_ZB_RESIDENT` (2) non-gzm cities are resident (LRU `drop_locked` in `gzm/registry.rs` = `live.stop()` + `stop_gzm_feed`), each dropped after `KB_ZB_IDLE_MIN` (30) min idle by a 60 s sweep. Wire stays the GZM dialect (`operator: "GZM"` = "seconds dialect"; the label comes from the registry client-side), shape ids `<slug>:<sanitised shape_id>.<rev6>` (`is_valid_shape_id`, `backend/src/api_helpers.rs`, gated by `zb_city_of` so `kb:`/`mzk:` never match the loose charset). Feeds expire on their own schedule (zbiorkom republishes); a slug with a 404 feed just stays `warming()`. Metro (route_type 1, Warsaw M1/M2): zbiorkom sends no metro positions, so `scheduled_tracks` (`gzm/state.rs`) places every running metro trip by its timetable (`schedule_position`, `gzm/parse.rs`, along the shape at the leg's timetable speed, ids `<slug>:1_S<sha1 of trip|date>`, `delay: null`, wire `scheduled: true` = dashed `veh-sched` pill, tooltip and trip note "z rozkładu"); a line any live type-1 record serves is skipped, GZM never schedules.

### Single-process assumption

The BB services, rate-limit buckets, stop-directions cache, the zbiorkom city registry and the road-shape store worker are all in-memory state in one long-lived process (the shape store file is additionally lock-guarded: a second process sharing `output/` stays read-only). Serverless or multi-instance deployment breaks rate limiting and multiplies upstream load. The BB services are one `static BB: LazyLock<Bb>` (`poller_singleton::bb()`, `backend/src/poller_singleton.rs`; building it starts nothing, `start_poller()` does), the zbiorkom cities live in `backend/src/gzm/registry.rs`: never construct `LivePoller`/`KbApi`/`GzmLive` in a route; go through those two.

## Gotchas

- **Python parity is intentional.** `py_truthy`, `parse_int_strict`, etc. in `backend/src/kb_api.rs` replicate Python truthiness/`int()` semantics and are used across the backend and routes; do not "simplify" them. Likewise "JSON parse errors are not retried" is parity, not an oversight. Where the port depends on JavaScript semantics that Rust does not share (`Math.round` halves, number formatting, collation), `backend/src/js.rs` has them: use it, not the std equivalent. An empty `{}` from a passthrough route means "upstream returned nothing" (e.g. vehicle not departed yet), not an error.
- **404 cache must not re-stamp.** In `fetch_positions` (`backend/src/poller.rs`) a candidate skipped due to a fresh cached 404 keeps its original timestamp: whenever scans come round faster than `KB_404_CACHE` expires, re-stamping would slide the TTL forever and permanently hide a late-dispatched bus.
- **Ghost vehicles.** Upstream never 404s dead trips; it keeps returning the last position. Filtering relies on movement anchors (`anchor_lat/anchor_lon/last_moved_at`, 15 m epsilon), staleness (frozen 300 s with no delay estimate), and `prune_dead`. The internal positions map may contain vehicles that `live_vehicles()`/`to_json()` deliberately hide.
- **Time math is agency-local.** All schedule math uses seconds-since-midnight in Europe/Warsaw (`KB_AGENCY_TIMEZONE`) via jiff (`backend/src/time.rs`, `now_secs()`), not server-local time, with ±43200 s midnight wrap: servers run UTC.
- **Upstream data quirks.** Positions can be bogus (0,0): rejected via a hardcoded service-area bbox (lat 48.8–50.5, lon 18.0–20.5). Stop coords arrive as micro-degrees (÷1e6). `trip_execution_id` is base64-encoded (`b64_exec_id`) before hitting upstream URLs. `/api/departures?places=` silently caps the response at **6 boards per request** (extra stops are just absent), hence `KB_BATCH_SIZE=6`; a board absent from the reply means truncation, not an empty stop (empty stops still get a board with empty rows), so the poller must not stamp the empty-cache for it.
- **Two stop ID spaces.** `Stop.urlId` (URL designator, may contain `:`; `url_id` server-side) vs numeric `internalId`/`stopId`. On the frontend, trip time entries match `time.designator → Stop.id` and `time.place_id → Stop.designator`: not interchangeable.
- **Vehicle icons key on line/color/operator/hasHeading, never the heading.** The animator rotates the `.veh-arrow` element in place (unwrapped angles so CSS never spins the long way); `setIcon` rewrites the DOM and replays the pop animation, so putting the bearing back into an icon key makes markers blink on every turn. `TripLayer` reads the live coords in its marker effect through `untrack()` on purpose (raw live coords only seed a new marker).
- **Motion clocks.** The engine runs on one local monotonic clock (`performance.now()`); server epoch seconds (`fix_at`) are mapped via the `X-Server-Time` offset. Never feed `Date.now()` or the KB `timestamp`/`updated_at` (= our fetch time) in as a fix time.
- **New passthrough routes must keep the security trio:** `is_valid_id`/`is_valid_date` input validation (blocks URL injection into upstream paths), `upstream_error()` (generic 502, never leaks upstream details), and the rate-limit gate. `/api/trip_execution` skips `is_valid_id` deliberately because the id is base64-encoded first.
- A new route is a module under `backend/src/api/` **plus**, in `backend/src/api/mod.rs`, its `Route` variant, its arm in `match_route` (a literal segment wins over a param one), its `dispatch_owned` arm and, when it takes more than GET, its `methods()`/`allow()` entries.
- `output/` is generated (GTFS feeds, logs), gitignored, and eslint-ignored: not stray files. `backend/target/` is cargo's, gitignored.
- 0 vehicles after midnight is normal; buses run ~4:30–22:00.
